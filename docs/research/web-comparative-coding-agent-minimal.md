# What “minimal” should mean for pi: an official-tools comparison

Date: 2026-08-28

## Bottom line

Pi should define **minimal** as a small, useful default capability set plus progressive disclosure—not as “no configuration” or “no safety boundary.” Adjacent official tools converge on five basics: one guided sign-in, one user config root, repository instructions, optional capability expansion, and a visible trust/approval model. Pi is unusually minimal in workflow policy: it starts with file/shell primitives and deliberately leaves MCP, subagents, plan mode, and permission prompts out of core ([pi README, “Philosophy”](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md#philosophy)). That is a coherent distinction, but the comparison suggests preserving project trust and making the safe baseline obvious.

## Implications for pi

1. **Auth: one happy path, broad capability behind it.** Keep `/login` as the primary onboarding path and environment variables as the automation path. Provider breadth is valuable, but it should not make first run feel like provider configuration work.
2. **Config: zero-file startup, one obvious user file, project config only when justified.** Pi’s two principal settings scopes are easier to understand than the more fragmented adjacent schemes. Avoid adding new core files for features that can remain extension-owned.
3. **Capabilities: primitives in core, integrations on demand.** The default file/shell tools are a good minimal kernel. MCP should remain optional unless repeated interoperability costs exceed the dependency, tool-discovery, and trust surface it introduces. Prefer a package/extension only after a workflow recurs.
4. **Instructions: converge on `AGENTS.md`, keep compatibility cheap.** `AGENTS.md` is the strongest cross-tool repository convention; retaining `CLAUDE.md` compatibility lowers switching cost. Instructions must remain clearly distinct from enforceable policy.
5. **Safety: minimal must still have a boundary.** Keep project trust defaulting to `ask`, review third-party packages, and treat repository-controlled executable configuration differently from plain instructions. Because pi intentionally omits per-command approval and an OS sandbox, documentation and starter setups should prominently offer two explicit postures: **trusted local checkout with full tools** or **untrusted code in an external container/sandbox**.
6. **A minimal personal pi package should be subtractive.** Start with no package; add only proven cross-machine resources. Each extension should justify its startup cost, prompt/tool surface, credentials, and full-process privilege. “Available” should not mean “loaded by default.”

## Recommended definition

> A minimal pi setup authenticates one provider, works immediately with the core file/shell tools, reads conventional repository guidance, loads no optional executable integration without an explicit user or trust decision, and adds configuration or packages only to remove recurring friction.

This preserves pi’s differentiator—workflow-neutral extensibility—while matching the baseline usability and trust expectations established by official adjacent tools.
