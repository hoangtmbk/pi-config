# Named peer pi sessions that message each other (primary sources)

Question: how to let several human-started pi sessions ("alice" in one terminal, "bob" in another) send each other messages that the receiving agent reads and can answer. Researched against pi.dev docs, the `earendil-works/pi` source at `9767ba2` (2026-09-06, `@earendil-works/pi-coding-agent` 0.85.1), and the ecosystem packages' own source.

## Recommendation

Build it as a **single small extension, file-based, no daemon**, on top of three pi primitives that already exist: `--name`/`pi.getSessionName()` for identity, `pi.sendMessage({...}, { triggerTurn: true, deliverAs: "steer" })` for delivery into the receiving agent, and `session_start`/`session_shutdown` for a registry entry plus an `fs.watch` on a per-name inbox directory. That is exactly the shape `pi-messenger` (the most-used peer-messaging extension, 701 stars) has converged on, and pi has no built-in equivalent to reuse: the stdio RPC protocol has no cross-process reach, and the Unix-socket "server/coordinator" in `src/experimental/` is deliberately source-only and not part of the supported API. ([pi-messenger — How It Works](https://github.com/nicobailon/pi-messenger#how-it-works), [CHANGELOG 0.85.1](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md))

Before writing one, try `pi install npm:pi-messenger` and see whether its `join`/`send`/`broadcast` cover the need; write a custom extension only if you want session names to be the pi `--name` rather than messenger's generated names, or want a smaller surface than its crew/team layers.

## What pi provides today

### 1. A session has a name, an id, and a file

- `pi --name <name>` / `-n` sets the display name at startup; `/name <name>` sets it later. The name is stored as a `session_info` entry in the session JSONL: `{"type":"session_info","id":"…","parentId":"…","timestamp":"…","name":"Refactor auth module"}`. ([Sessions — Naming Sessions](https://pi.dev/docs/latest/sessions#naming-sessions), [Session Format — SessionInfoEntry](https://pi.dev/docs/latest/session-format#sessioninfoentry))
- Extensions read/write it: `setSessionName(name: string): void` and `getSessionName(): string | undefined` on `ExtensionAPI`. `getSessionName()` walks entries in reverse for the latest `session_info` entry. ([extensions.md — pi.setSessionName](https://pi.dev/docs/latest/extensions#pisetsessionnamename), `packages/coding-agent/src/core/extensions/types.ts:1388-1391`, `packages/coding-agent/src/core/session-manager.ts:1164-1175`)
- Name changes fire `session_info_changed` — "Fired when the current session display name is set via `/name`, RPC, or `pi.setSessionName()`"; handler gets `event.name` (normalized, or `undefined` if cleared). ([extensions.md — session_info_changed](https://pi.dev/docs/latest/extensions#session_info_changed))
- The id and file: `ctx.sessionManager` is a `ReadonlySessionManager` exposing `getSessionId()`, `getSessionFile()`, `getCwd()`, `getSessionDir()`, `getSessionName()`. Files live at `~/.pi/agent/sessions/--<path>--/<timestamp>_<uuid>.jsonl`; the first line is `{"type":"session","version":3,"id":"uuid","timestamp":"…","cwd":"/path/to/project"}`. ([Session Format — File Location](https://pi.dev/docs/latest/session-format#file-location), [SessionHeader](https://pi.dev/docs/latest/session-format#sessionheader), `src/core/session-manager.ts:192-205, 1009-1025`)
- Shell commands run by the `bash` tool get `PI_SESSION_ID` and `PI_SESSION_FILE` (unset for `--no-session`), so a `bash`-driven fallback can also know who it is. Not injected into user `!` commands. ([Environment Variables — Shell Tool Session Environment](https://pi.dev/docs/latest/environment-variables#shell-tool-session-environment))
- Nothing records "this session is currently running" — `grep process.pid src/core src/main.ts src/modes` returns nothing. Session listing (`SessionManager.list(cwd, sessionDir?, onProgress?)`, `SessionManager.listAll(onProgress?)`) enumerates files on disk, live or not. ([Session Format — Static Listing Methods](https://pi.dev/docs/latest/session-format#static-listing-methods))

### 2. Injecting a message into a running agent (the receive side)

This is the load-bearing primitive. Verbatim signature:

```ts
sendMessage<T = unknown>(
  message: Pick<CustomMessage<T>, "customType" | "content" | "display" | "details">,
  options?: { triggerTurn?: boolean; deliverAs?: "steer" | "followUp" | "nextTurn" },
): void;
```
(`packages/coding-agent/src/core/extensions/types.ts:1365-1368`)

Option semantics from the docs ([extensions.md — pi.sendMessage](https://pi.dev/docs/latest/extensions#pisendmessagemessage-options)):

- `deliverAs: "steer"` (default) — "Queues the message while streaming. Delivered after the current assistant turn finishes executing its tool calls, before the next LLM call."
- `deliverAs: "followUp"` — "Waits for agent to finish. Delivered only when agent has no more tool calls."
- `deliverAs: "nextTurn"` — "Queued for next user prompt. Does not interrupt or trigger anything."
- `triggerTurn: true` — "If agent is idle, trigger an LLM response immediately. Only applies to `"steer"` and `"followUp"` modes (ignored for `"nextTurn"`)."

Implementation (`src/core/agent-session.ts:1474-1503`, `sendCustomMessage`): idle + `triggerTurn` starts a new turn; streaming + `triggerTurn !== false` queues as steer/followUp; streaming + `triggerTurn: false` is appended after the turn's tool results land (fixed in 0.84.x: "Fixed extension messages sent with `triggerTurn: false` while the agent is running being inserted between a tool call and its result"). So `{ triggerTurn: true, deliverAs: "steer" }` is the right shape for "bob receives alice's message whether idle or mid-turn". ([CHANGELOG](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md))

Custom messages "participate in LLM context" and are persisted as `CustomMessageEntry`; `display: true` shows them in the transcript, and `pi.registerMessageRenderer(customType, renderer)` can style them. ([extensions.md — pi.sendMessage](https://pi.dev/docs/latest/extensions#pisendmessagemessage-options), [Session Format — CustomMessageEntry](https://pi.dev/docs/latest/session-format#custommessageentry))

Alternative: `sendUserMessage(content: string | (TextContent | ImageContent)[], options?: { deliverAs?: "steer" | "followUp"; expandPromptTemplates?: boolean }): void` — "an actual user message that appears as if typed by the user. Always triggers a turn"; throws if streaming without `deliverAs`. Prefer `sendMessage` for peer messages so the model can tell it came from another agent, not the human. ([extensions.md — pi.sendUserMessage](https://pi.dev/docs/latest/extensions#pisendusermessagecontent-options), `examples/extensions/send-user-message.ts`)

The upstream `examples/extensions/file-trigger.ts` is the canonical minimal example of "external system injects a message": on `session_start` it does `fs.watch("/tmp/agent-trigger.txt", …)` and calls `pi.sendMessage({ customType: "file-trigger", content, display: true }, { triggerTurn: true })`. ([file-trigger.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/file-trigger.ts))

Important caveat on session replacement: `/new`, `/resume`, `/fork`, `/clone` emit `session_shutdown` on the old runtime, reload extensions with fresh instances, and emit `session_start` on the new one; "Old `pi` and command `ctx` references now throw instead of silently targeting the replaced session." A listener must re-register on every `session_start`, not once at factory time. ([extensions.md — Session replacement lifecycle and footguns](https://pi.dev/docs/latest/extensions#session-replacement-lifecycle-and-footguns), CHANGELOG entry on `withSession`)

### 3. Commands, tools, background listeners, UI

- `registerCommand(name: string, options: Omit<RegisteredCommand, "name" | "sourceInfo">): void` — gives `/send bob …`; handler `(args, ctx)` where `ctx` is `ExtensionCommandContext` (adds `waitForIdle()`, `newSession()`, `switchSession()`, …); optional `getArgumentCompletions(prefix)` for `/send <TAB>` name completion. ([extensions.md — pi.registerCommand](https://pi.dev/docs/latest/extensions#piregistercommandname-options))
- `registerTool(definition)` — `name`, `label`, `description`, `parameters` (TypeBox), `async execute()`, plus `promptSnippet` / `promptGuidelines` to tell the model when to use it (guidelines "must name the tool"). This is how the LLM itself sends to a peer. ([extensions.md — pi.registerTool](https://pi.dev/docs/latest/extensions#piregistertooldefinition))
- Background resources: "Do not start background resources such as processes, sockets, file watchers, or timers from the factory. Defer background resource startup until `session_start` … Register an idempotent `session_shutdown` handler". SIGTERM/SIGHUP now run `session_shutdown` "so extension resources (e.g. sockets) are released even when the terminal is gone". ([extensions.md — Long-lived resources and shutdown](https://pi.dev/docs/latest/extensions#long-lived-resources-and-shutdown), CHANGELOG #5080)
- UI: `ctx.ui.notify(message, type?: "info"|"warning"|"error")`, `ctx.ui.setStatus(key, text | undefined)` (footer), `ctx.ui.setWidget(key, string[] | componentFactory | undefined, options?)` (above/below editor), `ctx.ui.custom(component)` (TUI only). In RPC mode `notify`/`setStatus`/`setWidget` are forwarded as `extension_ui_request` lines; `custom()` is a no-op. (`src/core/extensions/types.ts:144-176`, [RPC — Extension UI Protocol](https://pi.dev/docs/latest/rpc#extension-ui-protocol))
- `ctx.mode` is `"tui" | "rpc" | "json" | "print"`, `ctx.hasUI` is true in TUI/RPC; use these to avoid `triggerTurn` in one-shot `-p` runs (edxeth's extension does `triggerTurn: ctx.mode !== "print"`). ([extensions.md — ctx.mode](https://pi.dev/docs/latest/extensions#ctxmode), `pi-subagents/src/subagents.ts:177`)
- Turn-state checks for smarter delivery: `ctx.isIdle()`, `ctx.hasPendingMessages()`, `ctx.abort()`; `agent_settled` event = "no automatic continuations queued; use for 'waiting for user' status". ([extensions.md — ctx.isIdle](https://pi.dev/docs/latest/extensions#ctxisidle--ctxabort--ctxhaspendingmessages), [agent_settled](https://pi.dev/docs/latest/extensions#agent_start--agent_end--agent_settled))
- `pi.events` (`EventBus`) is explicitly **intra-process** — "Shared event bus for communication between extensions" — it does not cross processes. ([extensions.md — pi.events](https://pi.dev/docs/latest/extensions#pievents))

### 4. Lifecycle events an inbox needs

`session_start { reason: "startup"|"reload"|"new"|"resume"|"fork", previousSessionFile? }`, `session_shutdown { reason: "quit"|"reload"|"new"|"resume"|"fork", targetSessionFile? }`, `session_info_changed { name }`, `agent_start`/`agent_end`/`agent_settled`, `turn_start`/`turn_end`, `tool_call`/`tool_result` (presence/activity), `before_agent_start` (inject a system-prompt line like "You are session alice; peers: bob"). ([extensions.md — Events](https://pi.dev/docs/latest/extensions#events))

### 5. Process-level interfaces (and why they do not solve it)

- **RPC mode** (`pi --mode rpc`) is stdin/stdout JSONL only — "No HTTP/sockets". Commands include `prompt`, `steer`, `follow_up`, `set_session_name`, `get_state`, `get_entries`; a parent process that *spawned* pi can inject text, but a sibling terminal cannot reach an interactive pi this way. ([RPC](https://pi.dev/docs/latest/rpc), [set_session_name](https://pi.dev/docs/latest/rpc#set_session_name))
- **SDK**: `createAgentSession({ sessionManager, … })`, `session.prompt/steer/followUp/subscribe`, `SessionManager.create/open/list/listAll`; "Running Multiple Sessions in One Process" is supported, but that is one host process, not peers in separate terminals. ([SDK](https://pi.dev/docs/latest/sdk))
- **`--name` in headless modes**: `--name` works "across interactive, print, JSON, and RPC modes" (0.79-era CHANGELOG entry #5153), so headless workers can be named the same way.

### 6. Not built in

`grep -ril "mailbox|broadcast|peer|swarm|team" src` hits only `src/experimental/**` and `package-manager.ts`. There is no session registry, inbox, socket, or cross-process message API in the supported extension surface, and `pi.dev/docs` has no page on multi-session messaging. The `examples/extensions/subagent/` example spawns `pi --mode json -p --no-session` children and captures their JSON output — strictly parent/child, no return channel. ([subagent/index.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/examples/extensions/subagent/index.ts), lines 15, 300, 346)

### 7. Experimental server/coordinator (present in source, not supported)

`packages/coding-agent/src/experimental/` contains a multi-process design: a detached **coordinator** on a Unix socket that "is only an opaque message router", a replaceable **server**, and one **session worker** per session; `CoordinatorConnection` has `send`/`broadcast`, `peer_connected`/`peer_disconnected` messages, and `~/.pi/server` (`PI_SERVER_DIR`, `PI_SERVER_ID`). The `mini/` README describes the topology: TUIs attach over `~/.pi/agent/experimental/mini.sock`; "Starting `mini` twice attaches two presentations to the same session; both see the same transcript, live." Supporting packages `@earendil-works/pi-protocol` (CBOR, protocol v8), `pi-client`, `pi-server` shipped in 0.84.0 as "experimental remote-session client APIs". ([coordinator.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/experimental/coordinator.ts), [server.ts](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/experimental/server.ts), [mini/README.md](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/experimental/mini/README.md), [packages/protocol/README.md](https://github.com/earendil-works/pi/blob/main/packages/protocol/README.md), [CHANGELOG 0.84.0](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md))

Status as of 0.85.1: "The experimental `client` and `experimental/plugin` subpaths and server/client commands are now source-only through `pi-test.sh`; the supported local SDK and stdio RPC API are unchanged" (#9132). `package.json` excludes `dist/experimental` from the published files. It is about **many presentations attached to one session**, not sessions messaging each other — the "peers" are coordinator connections, and `SessionManagement` exposes only `create`/`attach`/`detach`. Watch it, do not build on it. ([CHANGELOG 0.85.1](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md), `packages/coding-agent/package.json` `files`, `src/experimental/services/sessions.ts`)

Takeaway: every extension that delivers into a live pi agent uses the same call, `pi.sendMessage(..., { triggerTurn: true, deliverAs: "steer" })`. The only design axis that differs is the transport: **files + `fs.watch` + PID liveness** (pi-messenger) versus **tmux `send-keys` into the pane** (subagent extensions). `send-keys` needs a multiplexer, flattens newlines, and makes the message look human-typed; the file inbox needs neither and lets the model see a distinct `customType`.

## Comparative designs (official docs only)

- **Claude Code cross-session messaging** (closest analogue to the request): tools `ListAgents` and `SendMessage`; a session "answers to the name you set with the `/rename` command or the `--name` flag"; same-machine delivery is "Over a per-session socket … never through Anthropic servers" (Unix domain socket under `/tmp/cc-socks-<uid>`, path exported as `CLAUDE_CODE_MESSAGING_SOCKET`, optional `{"type":"auth","token":…}` first line); "Each session registers itself in files on disk" for discovery; duplicate names get renamed to a variant; delivery is "between tool calls during an active turn … When the receiving session is idle, Claude Code starts a new turn"; receiver is told the message "came from another session, not from you" and it "can't approve anything"; inbound policy `crossSessionInbound: accept | hold | refuse`; loops throttled ("drops identical repeats … queues at most 50"); `notify_when_idle` one-shot subscription. ([Message your other Claude Code sessions](https://code.claude.com/docs/en/cross-session-messaging), [#message-delivery](https://code.claude.com/docs/en/cross-session-messaging#message-delivery), [#the-sessions-inbox-socket](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket), [#control-inbound-messages](https://code.claude.com/docs/en/cross-session-messaging#control-inbound-messages))
- **Claude Code agent teams**: lead + teammates; "Each agent's mailbox is a JSON file at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`"; team config `~/.claude/teams/{team-name}/config.json` with a `members` array "Teammates can read this file to discover other team members"; split panes need tmux/iTerm2; "One team per session", "No nested teams". ([Agent teams — Architecture](https://code.claude.com/docs/en/agent-teams#architecture), [#limitations](https://code.claude.com/docs/en/agent-teams#limitations))
- **Codex CLI**: named subagents (`default`, `worker`, `explorer`, custom TOML in `~/.codex/agents/`), `/agent` switches threads, `[agents]` config (`enabled`, `max_concurrent_threads_per_session`, …); the docs "don't address whether independently started CLI sessions can message each other". ([Codex — Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents))
- **OpenCode**: `@general` mentions and Task-tool subagents with parent/child session navigation keybinds; "No cross-session messaging or session sharing is mentioned". ([OpenCode — Agents](https://opencode.ai/docs/agents/))
- **Gemini CLI**: Markdown+YAML subagents with `name`; "subagents cannot call other subagents"; results "report back to the main agent". ([Gemini CLI — Subagents](https://geminicli.com/docs/core/subagents/))

Design ideas worth stealing: Claude's *sender label + reply address* in the delivered text, the *"not from the user, cannot approve"* framing, per-session *inbound policy*, *dedupe/loop throttling*, and *name-collision renaming*; Claude teams' *readable config for discovery*.

## What would have to be built

Everything below is absent from pi and must live in an extension (or a package wrapping one):

1. **Registry** of live sessions: on `session_start`, write `~/.pi/agent/peers/<name>.json` with `{ name, pid, sessionId, sessionFile, cwd, startedAt }` where `name = pi.getSessionName() ?? <generated>`; rewrite on `session_info_changed`; delete on `session_shutdown`. Liveness by `process.kill(pid, 0)`, as pi-messenger does, because pi records no PID itself.
2. **Inbox** per name: `~/.pi/agent/peers/inbox/<name>/<ts>-<uuid>.json`; `fs.watch` it from `session_start`, drain in sorted order, delete after delivery; guard against re-entrancy (pi-messenger's `isProcessingMessages` flag).
3. **Delivery**: `pi.sendMessage({ customType: "peer_message", content: "**Message from alice** (reply: peer_send to=alice)\n\n…", display: true, details }, { triggerTurn: true, deliverAs: "steer" })`; skip `triggerTurn` when `ctx.mode === "print"`.
4. **Send side**: a tool `peer_send({ to, message })` and `peer_list()` for the model, a `/send <name> <text>` command with `getArgumentCompletions` over the registry for the human, optional `broadcast`.
5. **Prompt context**: in `before_agent_start`, append "You are pi session `<name>`. Peers: …" so the model knows its own name and how to reply; `promptGuidelines` on the tool.
6. **Rendering**: `registerMessageRenderer("peer_message", …)`, `ctx.ui.setStatus("peers", "2 peers · 1 unread")`.
7. **Hygiene**: name collision handling when two terminals start `--name alice`, stale registry cleanup, message size cap, a per-sender rate limit / identical-repeat drop to stop two agents ping-ponging, and an opt-in inbound policy (accept / hold / refuse) mirroring Claude's `crossSessionInbound`.

Rough size: pi-messenger's core (`index.ts` + `store.ts` + `lib.ts`, without crew/team/overlay) is the reference for how small this can be.

## Gaps and open questions

- **No supported cross-process API in pi.** RPC is stdio-only; `pi.events` is in-process; the Unix-socket coordinator is experimental and unpublished. Whether upstream intends to expose the experimental server as a supported multi-session surface is not stated anywhere in docs or CHANGELOG. ([RPC](https://pi.dev/docs/latest/rpc), [CHANGELOG 0.85.1](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/CHANGELOG.md))
- **No "running sessions" list.** `SessionManager.list/listAll` see files, not processes, so a registry with PIDs is unavoidable; PID liveness is host-local and breaks across containers.
- **Names are not unique.** `--name` is a display name; nothing prevents two live sessions named `alice`, and a name changes mid-session via `/name`. The registry must decide collision policy (refuse, or suffix like Claude Code's "variant").
- **`--name` vs generated names.** pi-messenger ignores pi's session name and generates its own; a custom extension can key on `pi.getSessionName()` but then unnamed sessions need a fallback.
- **Delivery during a long tool call.** `deliverAs: "steer"` waits for the current tool call to finish; a message cannot interrupt a blocking `bash`. Whether that is acceptable, or whether `ctx.abort()` should ever be used, is a product decision.
- **Headless peers.** `triggerTurn` in `-p` mode ends the run once; a long-lived headless worker that can receive would need `--mode rpc` under a driver, or an idle loop that pi does not provide.
- **Security.** Extension code runs with full user privileges; an inbox dir under `~/.pi/agent` is writable by anything running as that user. pi has no equivalent of Claude's socket auth token or "sender cannot approve" framing — that framing has to be in the injected text.
- **Multi-root and worktrees.** pi-messenger scopes some state per project (`.pi/messenger/`) and some globally; a peer design must choose whether `alice` in repo A can reach `bob` in repo B by default.
- **Unverified ecosystem entries.** `pi-messenger-swarm`, `pi-ultra-messenger`, `@narumitw/pi-subagents` ("Asynchronous main-agent messaging") could not be fetched (npm 403 / not cloned); their transports are unknown.
