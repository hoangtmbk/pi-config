The Handoff writer's instruction (prototype)

Throwaway prototype for The Handoff writer's instruction, part of the Self-compaction extension for pi. Not production code.

Question: what exactly does the writer get told, in fork mode and in serialized mode, and how does code turn its reply into the Handoff's details? Pick a mode, a trigger and a sample reply, then press Run the writer. You'll see the exact text the writer receives, whether its reply is accepted or counts as a failure, which ledger quotes pass the quote check, and the Handoff the agent will read next.

Shape: the question is about data shape and parsing, not looks, so this is a logic prototype. The sample conversation and the replies are hand-written stand-ins for what a model would produce. No model is called.

Points to react to

  1. As of now, not as of the cut. Both modes write the Handoff as of the end of the conversation, tail included, so Next step never points at work the tail already did. Serialized mode therefore also gets the kept tail (marked as kept). That widens the serialized quote check in What a Handoff must carry to include the tail too.
  2. Full sections, not a diff. On a repeat compaction the writer outputs all six sections again, edited from the previous Handoff. A diff format is fragile, and code would have to apply it.
  3. Failure = strict shape. No <handoff> block, any of the six headings missing, or an empty or "(none)" Goal or Next step means the reply failed and the next writer in the chain runs. So do an error or length stop. A tool call next to a valid block is ignored, not a failure.
  4. Ledger entries carry no kind. Rule, preference and exclusion aren't labelled, which leaves less for the writer to get wrong. Compaction focus is the only separate kind, and code writes it, not the writer.
  5. Quotes under 12 characters are dropped. Otherwise "ok" or "no" passes the substring check against almost anything.
  6. Self-compaction needs placeholder tool results. The fork runs inside self_compact's execute, so the assistant message ends in unanswered tool calls. Anthropic rejects a request where a tool_use has no tool_result, so the fork appends one result per pending call before the instruction.
  7. Serialized cuts are head and tail. Each tool result keeps 1,200 characters from the start and 800 from the end, because test failures and errors sit at the end. Pi keeps the first 2,000 only. If the request still doesn't fit, the budget halves, down to a floor of 200 characters, and after that it's a failure.
